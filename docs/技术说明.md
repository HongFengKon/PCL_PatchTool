# 技术说明

面向想看懂/维护这个工具的人。结论先行：**下载引擎没被删，只是三个入口被改成了"拒绝"**，
所以修复的本质是"把入口接回去"，而不是重新实现下载。

---

## 1. 被改写的三处入口

以 `PCL 正式版 2.99.0.0 (413)` 为例。

### 1.1 下载页加载器

`PCL.PageDownloadInstall.LoaderInit()` 里，本该把 `LoadMinecraft` 这个 Loading 控件
绑到真实的版本列表加载器：

```il
ldarg.0
ldarg.0
callvirt  PCL.MyLoading PCL.PageDownloadInstall::get_LoadMinecraft()
...
ldsfld    PCL.ModLoader/LoaderTask`2<System.String,PCL.ModDownload/DlClientListResult> PCL.ModDownload::DlClientListLoader
```

被改成了构造一个"一启动就抛异常"的临时加载器：

```il
ldstr     "关闭下载"
ldnull                                    ; cached delegate 检查
ldsfld    System.Action`1<...> PCL.PageDownloadInstall/_Closure$__::$IR3-3
brfalse.s ...
ldftn     PCL.PageDownloadInstall/_Closure$__::_Lambda$__R3-3
newobj    System.Action`1<...>::.ctor
...
newobj    PCL.ModLoader/LoaderTask`2<...>::.ctor     ; 工作委托就是 _Lambda$__3-0 → throw
```

而 `_Lambda$__3-0` 的主体是：

```il
ldstr     "为遵守相关法律法规，PCL 暂时不再提供 MC 下载功能，非常抱歉 qwq……"
newobj    System.Exception::.ctor(string)
throw
```

结果就是：进入下载页 → 加载器 `关闭下载` 立刻 `Failed` → 页面空白。
**修复**：把 `[ldstr "关闭下载" … newobj LoaderTask]` 这段整体换成一条
`ldsfld PCL.ModDownload::DlClientListLoader`，和正常版本完全一致。

### 1.2 整合包安装分发

`PCL.ModModpack.ModpackInstall(String FileAddress, String InstanceName, String Logo)`
本身是"识别整合包种类 → 分发"，它的识别逻辑（读 zip、比对标记文件名）**原封不动**，
但分发用的 `switch` 整段被删掉，所有分支的 `leave` 全部改成跳到方法末尾的一句 `throw`：

```il
02DA  ldstr    "为遵守相关法律法规，PCL 暂时不再提供 MC 下载功能，非常抱歉 qwq……"
02DF  newobj   System.Exception::.ctor(string)
02E4  throw
```

注意它位于**外层 try 内部**（`try 0x0027..0x02E5`），ZipArchive 的 `Dispose` 在后面的
`finally` 里 —— 这个细节决定了补丁要插在哪、收尾块要放哪（见 §4.1）。

**修复**：在原来的 `throw` 位置生成分发代码，收尾块（`ldloc result; ret`）追加到
**方法末尾**（finally 处理块之后），并把外层 finally 的 `HandlerEnd` 指向收尾块。

### 1.3 本地导入整合包入口

`PCL.ModModpack.ModpackInstall()`（无参）被换成"只弹提示"：

```il
newobj  PCL.ModModpack/_Closure$__0-0::.ctor
stloc.0
ldstr   "为遵守相关法律法规…"
ldc.i4.2
ldc.i4.1
call    PCL.ModMain::Hint(string, HintType, bool)
ret
```

好消息是闭包类型 `_Closure$__0-0` 还在，并且它的 `$VB$Local_File` 字段和
`_Lambda$__0`（真正干活的线程体，内部调用三参数版 `ModpackInstall`）都**完好无损** ——
被摘掉的只有"选文件 + 起线程"这一层。

## 2. 不依赖老版：怎么"现场生成"正确答案

老版本的作法是"从正常 exe 里克隆 IL"。本工具改为按语义推导，全部依据**目标文件自身**的信息。

### 2.1 分发映射怎么来（不硬编码）

识别逻辑里不断出现这种模式：比较 zip 里的文件名 → 把种类编号写入同一个 int 局部变量。

```il
ldstr      "mcbbs.packmeta"
call       Operators::CompareString(...)
...
ldc.i4.3
stloc.s    V_4          ; ← 种类 = 3
```

于是工具：

1. 扫描所有 `ldc.i4.*` + `stloc`，把"附近 18 条指令内出现过已知标记文件名"的候选挑出来，
   得分最高的那个局部变量就是"种类变量"（`vKind`）；
2. 再对每个 `stloc vKind` 回溯最近的标记文件名，得到 **标记 → 种类值** 的真实映射；
3. 用这个映射去生成分支，而不是假设"0 就是 CurseForge"。

实测拿到的映射：`manifest.json→0、modpack.json→1、mmc-pack.json→2、mcbbs.packmeta→3、
modrinth.index.json→4、modpack.zip/mrpack→9`（5–8 保持默认走压缩包分支），
与正常版本完全一致。如果某个标记在新版本里消失，对应分支自动退化为默认分支，
而不是瞎猜。

### 2.2 其余局部变量怎么认

| 变量 | 识别方式 |
|---|---|
| `ZipArchive` | 唯一一个类型为 `System.IO.Compression.ZipArchive` 的局部变量 |
| 结果 `LoaderCombo<String>` | 类型名以 `PCL.ModLoader/LoaderCombo`1` 开头的局部变量 |
| `ArchiveBaseFolder` | 匹配 `ldnull; stloc; ldstr ""; stloc` 这个"先置空再初始化"的固定模式 |
| `kind` | 见 §2.1 的打分 |

### 2.3 参数顺序怎么保证

`InstallPack*` 的参数个数直接从**方法定义**读：

```
InstallPackCurseForge / InstallPackModrinth : 5  → arg0, Archive, BaseFolder, arg1, arg2
InstallPackMCBBS                            : 4  → arg0, Archive, BaseFolder, arg1
InstallPackHMCL / MMC / LauncherPack        : 3  → arg0, Archive, BaseFolder
InstallPackCompress                         : 2  → arg0, Archive
```

### 2.4 本地导入入口的"难点"

`MeloongCore.Wpf.Dialogs::SelectFile` 的签名是：

```csharp
List<string> SelectFile(string title, bool multiselect, string defaultDirectory,
                        Nullable<OneOf<IEnumerable<(string[], string)>, string>> filter)
```

第四个参数是 `Nullable<OneOf<...>>`。正常版本会用 `newarr ValueTuple` + `OneOf.op_Implicit`
+ `new Nullable<T>(...)` 一层层构造。工具走了一条更简单的等价路径：

```il
ldloca.s  V_new                 ; 新加一个该 Nullable 类型的局部变量
initobj   Nullable<OneOf<...>>  ; 默认值 == HasValue = false == VB 的 Nothing
ldloc.s  V_new
```

其余部分按正常结构生成（闭包 → SelectFile → `Enumerable.FirstOrDefault<String>` →
存回 `$VB$Local_File` → `IsNullOrEmpty` 判断取消 → `ModBase::RunInThread(_Lambda$__0)`）。
其中 `RunInThread` 用的是**新版里仍然存在的方法定义**（投毒只是把唯一的调用点删了，
方法本身还在，所以能直接 `call`）。

## 3. 生成的分发 IL（结构）

```
        ldloc    vKind
        switch   [case0 … case9]     ; 10 个目标
        br       compress

case0:  ldarg.0; ldloc Archive; ldloc BaseFolder; ldarg.1; ldarg.2
        call     InstallPackCurseForge
        stloc    vResult
        leave    landing
…（HMCL / MMC / MCBBS / Modrinth / LauncherPack 同构）

compress:
        ldarg.0; ldloc Archive
        call     InstallPackCompress
        stloc    vResult
        leave    landing

landing:                          ; ← 必须位于 finally 处理块之后
        ldloc    vResult
        ret
```

`switch` 的每个目标都是对应分支块的第一条指令；没有映射到的种类值指向 `compress`。

## 4. 踩过的坑（维护时值得注意）

### 4.1 收尾块的位置

第一版把 `landing; ret` 直接接在插入的分发代码后面，结果它落在了 `finally` 处理块
**之前**，异常表变成 `handler 0x03B7..0x03B2`（结束早于开始），文件写出来能过 Cecil、
一跑就炸。正确做法是：分发代码插在原 `throw` 处，收尾块**追加到指令表最末尾**，
然后 `HandlerEnd = landing`。

### 4.2 `stloc` 有宏指令形式

VB 编译器会输出 `stloc.0` / `stloc.1` / `stloc.s V_4`，而 `OpCodes.Stloc` 只对应带操作数的
长形式。只判断 `OpCodes.Stloc` 会漏掉全部 `stloc.1/2`，导致"局部变量识别不出来"。
工具里统一用 `IsStloc()` + `StlocVar()`（后者按宏编号回查 `body.Variables[i]`）。

### 4.3 JIT 与 AssemblyResolve 的顺序

`AssemblyResolve` 只能拯救"**调用之后**才 JIT 的代码"。如果 `Main` 方法体里直接出现
Cecil 类型，JIT 在方法入口就会解析类型引用 —— 此时事件还没注册，直接
`FileNotFoundException`，而且在这种环境下连异常文本都打不出来。
所以 `Main` 必须保持"零 Cecil 引用"，Cecil 只在被调用之后的方法里出现。

### 4.4 临时目录不一定可写

某些受限环境/企业策略下，子进程写 `%TEMP%` 会被拒绝（`UnauthorizedAccessException`）。
工具用回退链：`%TEMP%` → `%LOCALAPPDATA%\Temp` → exe 所在目录，全失败才报错。

## 5. 写盘前的校验

写出 `<原名>.pclfix.tmp` 后，**重新读回来**验证：

1. 三处补丁各自的特征是否出现：
   - `PageDownloadInstall.LoaderInit` 里有 `ldsfld ...DlClientListLoader`
   - `ModpackInstall(3)` 里有 `switch`
   - `ModpackInstall(0)` 里有 `call ...SelectFile`
2. 全程序集结构自检 `ValidateStructure()`：
   - 每个异常处理块：`TryEnd ≥ TryStart`、`HandlerEnd ≥ HandlerStart`
   - 每条 `br` / `leave` / `switch` 的目标都必须是**同一个方法体内**的指令

任一不通过 → 删除临时文件，原文件一动不动。只有全过才会
`备份为 .bak → 删除原文件 → 重命名临时文件`。

## 6. 适配未来版本

如果 PCL 以后换版本号、改了这些方法：

| 现象 | 工具表现 | 该做什么 |
|---|---|---|
| 三处都找不到投毒特征 | 报「未找到」，退出码 1 | 说明这个版本本来就有下载，或投毒方式变了 |
| 找不到 `"关闭下载"` 加载器 | P1 报「未找到」 | 去看新版 `LoaderInit` 现在长什么样 |
| 找不到 `ldstr 法律法规 + newobj + throw` 三连 | P2 报「未找到」 | 同上 |
| 局部变量认不出 | P2 报「跳过」并列出缺哪个 | 补 §2.2 的识别规则 |
| 缺 `SelectFile` / `RunInThread` / 闭包字段 | P3 报「跳过」 | 看新版换了什么 API |

设计上宁可「跳过并说明」，也不在学生不确定的地方硬改。这三个补丁互相独立，
一个失败不影响另外两个。

## 7. 为什么不用"重新编译"

PCL 是 VB.NET + WPF，完整还原构建环境不现实；而且我们只需要改 3 个方法体。
用 Mono.Cecil 做"读 IL → 改方法体 → 写回"可以保证：

- 其余方法、资源（XAML 的 `g.resources`、内嵌的 14 个依赖程序集）原样保留
- 不需要强名称签名处理（PCL 未签名）
- 改完是标准 PE 映像，WPF/.NET Framework 直接加载

唯一代价：写盘时 Cecil 需要解析被引用的依赖程序集（为了确定某些参数默认值的枚举底层类型）。
PCL 把所有依赖**内嵌在自身资源里**，所以工具会先把这些资源里的 `MZ` 字节流
解出来到临时目录，挂到 `DefaultAssemblyResolver` 上，再读写。
